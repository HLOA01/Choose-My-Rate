# Cross-origin application navigation rehearsal (TEST only)

This branch enables no real receiver. LendingPad is the selected destination, but the account-inspected POS URL reached a staff login; that observation is not borrower-form or application-receipt evidence. No verified tenant URL is installed, no API is invented, and src/ is unchanged.

Run npm run qa:cross-origin-application. The existing Funnel is served on one explicit 127.0.0.1 HTTP origin and a static synthetic receiver on the next port. Configuration rejects non-loopback URLs, credentials, missing/overflow ports, path/query/fragment ambiguity before resources start. The receiver requires TEST_SYNTHETIC, binds only 127.0.0.1 and supports GET navigation/health only. All pricing/platform responses are synthetic and nonlocal requests are blocked. No credentials, lender connection, loan creation, database or external service is used. Normal browser QA excludes this file because it requires its separate receiver configuration; CI runs it explicitly after ordinary and same-origin configured-redirect QA.

Three cases use the ACTUAL existing CTA: a mock application page, an actual HTTP302 to synthetic staff login, and HTTP503 unavailability. Each verifies a GET to the exact fixed configured URL with no request body or appended scenario/quote parameters; a synthetic source-query sentinel is absent from the cross-origin referrer, which contains only the origin. The foreign page cannot read CMR sessionStorage. No application.started is emitted on click/load/redirect/error/return/reload, and return/reload clears the old prepared selection. Partial-fee disclosure remains on CMR before leaving.

Limits: this characterizes link navigation, not a receiver adapter. A loaded page, login redirect or HTTP status cannot establish application acceptance. The existing CTA does not detect that the external page is a borrower form; this test does not add such a check. Existing sessionStorage preparation still occurs on the CMR origin and is not sent across origins. Shared browser/device isolation or authentication is not established by storage origin isolation. Existing same-origin tests cover missing destination and storage failures; these three cases do not replace them. A future provider-specific path requires the actual verified public borrower Apply/resume workflow; API transfer and acknowledgement need documented enabled schema/authentication/receipt semantics. No production deployment/configuration change is included.
